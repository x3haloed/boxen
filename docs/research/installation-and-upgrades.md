# Installation and upgrades

Boxen should install as a native desktop application with a daemon that starts at boot. Daemon upgrades should stage in the background and apply automatically when the executing host has no runs in flight. GitHub Releases can host the full artifacts and binary deltas. A desktop update that takes effect inside the same open window requires a new boundary in the desktop architecture. Installation and updater implementation are deferred.

## Platform installation

| Platform | Proposed installation | Considerations |
| --- | --- | --- |
| macOS | A signed, notarized `.pkg` installs `/Applications/Boxen.app` and a boot-time `launchd` LaunchDaemon. The desktop and daemon have independent executable locations. | A bundled daemon registered through `SMAppService` is an option on macOS 13 and later, subject to background-item approval. The current development bundle declares macOS 12 and uses an ad-hoc signature. [Apple distribution packaging](https://developer.apple.com/documentation/xcode/packaging-mac-software-for-distribution) · [Apple service management](https://developer.apple.com/documentation/servicemanagement/smappservice?language=objc) |
| Windows | A signed WiX MSI installs the desktop `.exe` and daemon under `Program Files` and registers an automatic Windows Service. | The foreground daemon needs a Service Control Manager entry point or a small wrapper that translates service start and stop into daemon lifecycle operations. Interactive addons run in the user's session. [WiX service installation](https://docs.firegiant.com/wix/schema/wxs/serviceinstall/) · [Windows service entry point](https://learn.microsoft.com/en-us/windows/win32/api/winsvc/nf-winsvc-startservicectrldispatcherw) · [Windows interactive services](https://learn.microsoft.com/en-us/windows/win32/services/interactive-services) |
| Linux | Start with the portable APE in versioned directories and the documented systemd user service. Enable lingering where boot startup is needed. | Add distro-native packages when needed. Distro package managers own updates to their installed files. The portable installation can use Boxen's updater. [Boxen's systemd recipe](../resident-preparation.md#durable-linux-service) · [systemd user services and lingering](https://www.freedesktop.org/software/systemd/man/devel/systemd-run.html) |

Adopt existing installations with a full baseline release. Configure the service with the intended unprivileged account, explicit data directory and backend settings. Preserve the machine identity, journals, peer configuration, and existing resident working directories. Verify backend access from the actual boot context, since a service can see a different home, credential store, or executable search path from an interactive shell. Keep executable installation and local state in separate locations. The desktop must still be able to reach the authenticated loopback API under the intended local-user access controls. [Daemon and desktop attachment](../desktop.md#build-and-launch) · [Client authentication](../client-api.md)

## Automatic daemon upgrades at idle

1. Download, reconstruct if needed, and verify the new release while the current daemon runs.
2. At a convenient idle point, check for accepted nonterminal runs and briefly pause new execution admission under the same synchronization boundary. Local and peer requests, scheduled work, mail and observation activations, and other run entry points share this rule. A start that wins the race makes the updater defer. Once the pause wins, preserve durable pending inputs and make retryable admission failures explicit.
3. Stop the service, switch to the staged executable, and restart. Verify the expected release version, existing machine identity, and authenticated API readiness. Resume dispatch through the existing authorities. A busy host keeps running and can apply the staged upgrade later.
4. Retain the previous executable for failed startup recovery. Automatic binary rollback requires compatible on-disk state. Rolling back an executable leaves journals and tool effects in place.

The desktop stays open during this sequence. The local connection briefly drops, workloads on other hosts can continue, and the client reconnects and replays retained events. A daemon crash still records unfinished execution as interrupted with uncertain effects. The idle admission boundary is what prevents a planned upgrade from creating that outcome. [Workload recovery](../workloads.md) · [Desktop replay and recovery](../desktop.md#execution-and-recovery)

Service registration and protected install paths require platform authorization. Any future unattended installer helper should have narrowly scoped authority to verify a release, switch the managed payload and control the specific Boxen service. An ordinary workload or a writable staging directory cannot be trusted to choose code for an elevated helper to execute.

## Desktop updates while the window is open

| Approach | User experience | Work required |
| --- | --- | --- |
| Apply on natural quit | The desktop stays open throughout normal use. New code runs the next time the desktop opens. | Conventional background staging. A desktop that rarely quits can stay on an older build for a long time. |
| Relaunch and restore | The window briefly disappears and comes back in the same workspace. | Build on saved docking, per-thread drafts and exact unresolved submissions. Capture transient state such as new-thread form text, restore focus and scroll as needed, and ensure handoff preserves submission semantics. |
| Swap UI code in the same window | Updated panels render inside the existing native window. Updates to the host, renderer, or compatibility boundary still require a relaunch. | Keep the native window, event loop and GPU renderer in a stable host. Put replaceable UI code behind a versioned interface and hand off state at a frame boundary. |

The desktop currently enters `eframe::run_native` as a single linked Rust program. Replacing files on disk affects later launches. A live swap needs a boundary around replaceable code, with explicit ownership of callbacks, workers and state. A signed module could use a narrow C ABI and versioned data, with the host retaining the previous module until the new one initializes and renders successfully. Rust's default ABI offers no stability guarantee for sharing Boxen's existing Rust and egui types between independently released binaries. macOS library validation also needs testing with the final signing and installation layout. [Desktop entry point](../../desktop/src/main.rs) · [Rust ABI reference](https://doc.rust-lang.org/reference/items/external-blocks.html) · [Apple library validation](https://developer.apple.com/documentation/BundleResources/Entitlements/com.apple.security.cs.disable-library-validation)

If same-window activation becomes a priority, prototype swapping one real Boxen panel while a remote transcript streams and a draft is open. Check that the original native window and focus survive, every event appears once, unresolved requests retain their exact identity, and a broken module leaves the previous UI usable. The proposed initial release uses apply-on-quit.

## Delta downloads from GitHub Releases

Publish full artifacts for each supported target and direct deltas from one or two recent published bases. A signed manifest binds the exact base, patch and target hashes to the release and target platform. Use the latest release for discovery and immutable tagged assets for downloads. Stage the reconstructed artifact, verify its target hash and any required platform signature, then activate it. An unknown base, a locally modified build, or a failed reconstruction uses the verified full artifact. [GitHub release links](https://docs.github.com/en/repositories/releasing-projects-on-github/linking-to-releases) · [Immutable releases](https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases)

A local Zstandard `--patch-from` trial between two distinct macOS desktop executables produced a 4.03 MiB patch against a 6.72 MiB compressed full executable, about 40% smaller. Applying the patch reproduced the target SHA-256 exactly. The trial covered one executable pair. Signed bundles, Windows payloads and APE deltas need their own measurements. Generate production deltas from final release payloads and retain the exact published bases. [Zstandard patching](https://github.com/facebook/zstd/wiki/Zstandard-as-a-patching-engine)

Sparkle fits Mac app-bundle deltas with apply-on-quit or relaunch. Sparkle's `.pkg` update flow has no delta support. Velopack supports Windows deltas and a per-machine MSI, but its normal apply flow replaces the current directory and can terminate processes that hold it open. It is a candidate for conventional desktop updates. The service upgrade and any same-window desktop activation need their own lifecycle coordination. [Sparkle deltas](https://sparkle-project.org/documentation/delta-updates/) · [Sparkle package updates](https://sparkle-project.org/documentation/package-updates/) · [Velopack Windows updates](https://docs.velopack.io/packaging/operating-systems/windows)

## Release verification

Start with native installers and a full baseline, then verify automatic idle daemon upgrades and delta fallback on one host before rolling through the other installations. Exercise clean install, reboot without login, adoption of existing identity and state, real backend access under the service account, and authenticated local and peer access across mixed versions. Race a start request and an automatic activation against the idle transition. Exercise bad patches, interrupted staging, failed service startup and compatible rollback. Check reconstructed signed artifacts and keep the existing portable executable verification in the release rotation. The installer, idle handoff and live UI swap remain untested.
